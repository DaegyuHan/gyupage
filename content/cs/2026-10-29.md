## 컨텍스트 스위칭은 공짜가 아니에요
CPU 코어 하나는 한 번에 하나의 스레드만 실행해요. 스레드가 코어보다 많으면 OS 스케줄러가 번갈아 실행시키는데, 이때 레지스터·프로그램 카운터 같은 상태를 저장하고 복원하는 작업이 컨텍스트 스위칭이에요.

직접 비용은 마이크로초 단위지만, 진짜 비용은 간접 비용이에요. 다른 스레드가 돌면 CPU 캐시와 TLB가 오염돼서 복귀 후 캐시 미스가 늘어나요. 그래서 스레드가 너무 많으면 "일하는 시간"보다 "교대하는 시간"이 커져요.

## 풀 크기는 작업 성격으로 잡아요
| 구분 | 특징 | 풀 크기 감각 |
|---|---|---|
| CPU-bound | 계산, 암호화, 압축 | 코어 수 ~ 코어 수+1 |
| I/O-bound | DB, 외부 API 대기 | 코어 수 × (1 + 대기시간/연산시간) |

I/O 대기 중인 스레드는 CPU를 쓰지 않으니 코어 수보다 많아도 괜찮아요. 예를 들어 8코어에서 요청당 연산 10ms, 대기 90ms라면 8 × (1+9) = 약 80개가 출발점이에요.

```java
int cores = Runtime.getRuntime().availableProcessors();
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    cores, cores * 4,
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200),          // 무제한 큐 금지
    new ThreadPoolExecutor.CallerRunsPolicy());
```

## 자주 하는 오해와 함정
- **"스레드 늘리면 처리량도 늘어난다"**: 병목이 DB 커넥션 풀(예: 10개)이라면 Tomcat 스레드를 200→500으로 올려도 커넥션 대기만 길어져요.
- **공식은 정답이 아니라 시작점**: 실제로는 부하 테스트로 p99 지연과 처리량을 보며 조정해요.
- **무제한 큐**: `Executors.newFixedThreadPool`은 큐가 무제한이라 밀린 작업이 쌓이다 OOM이 날 수 있어요.
- **컨테이너 환경**: CPU limit이 있어도 구버전 JVM은 호스트 코어 수를 읽을 수 있어서 `availableProcessors()` 값을 확인해야 해요.

<!-- practice -->
- 트래픽이 몰릴 때 Tomcat maxThreads를 200에서 800으로 올렸더니 오히려 응답이 느려졌어요. 스레드 덤프와 HikariCP 대기 지표(pending)를 보면 커넥션 풀이 진짜 병목인지 확인할 수 있어요.
- 코드 리뷰에서 `Executors.newFixedThreadPool(100)`을 쓴 PR을 봤어요. 큐 무제한 위험과 CPU-bound/I/O-bound 구분 없이 정한 크기를 지적하고, 큐 크기·거절 정책을 명시하자고 제안해요.
- 이미지 리사이징 같은 CPU 집중 작업을 I/O용 공용 풀에서 돌렸더니 API 응답까지 느려졌어요. 작업 성격별로 풀을 분리(bulkhead)하고 각각 크기를 다르게 잡아요.
