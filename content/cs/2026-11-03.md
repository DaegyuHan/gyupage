## @Transactional의 정체는 프록시예요

스프링은 `@Transactional`이 붙은 빈을 **프록시 객체**로 감싸요. 외부에서 메서드를 호출하면 프록시가 먼저 트랜잭션을 시작하고, 실제 메서드를 실행한 뒤, 예외 여부에 따라 commit/rollback을 해요. 즉 "프록시를 거쳐야" 트랜잭션이 걸려요. 롤백 이슈는 대부분 여기서 출발해요.

## 롤백이 안 되는 대표 함정 3가지

| 상황 | 이유 | 해결 |
|---|---|---|
| 같은 클래스 내부 호출 (`this.save()`) | 프록시를 우회해서 어드바이스가 안 붙음 | 빈 분리, 구조 개선 |
| checked 예외 (`IOException` 등) | 기본은 `RuntimeException`/`Error`만 롤백 | `rollbackFor = Exception.class` |
| `try-catch`로 예외를 삼킴 | 프록시는 예외가 밖으로 나와야 롤백을 알아요 | 다시 던지기 |

```java
@Service
public class OrderService {

    public void placeOrder() {   // 트랜잭션 없음
        save();                  // this.save() → 프록시 우회!
    }

    @Transactional
    public void save() {
        orderRepository.save(new Order());
        throw new IllegalStateException(); // 롤백 안 됨
    }
}
```

## 실무에서 더 헷갈리는 부분

- **private/final 메서드**: CGLIB 프록시가 오버라이드할 수 없어서 적용되지 않아요. 
- **UnexpectedRollbackException**: 바깥 `REQUIRED` 트랜잭션에 참여한 안쪽 메서드에서 예외가 나면 rollback-only가 마킹돼요. 바깥에서 catch해서 정상 종료해도 commit 시점에 이 예외가 터져요.
- **`REQUIRES_NEW`도 self-invocation이면 무의미**해요. 새 트랜잭션이 안 열려요.

면접에서는 "어노테이션 규칙"을 외우기보다 **"프록시가 어디서 예외를 보는가"**로 설명하면 깊이가 드러나요.

<!-- practice -->
- 주문 저장 후 알림 발송 메서드에서 `catch (Exception e) { log.error(...) }`로 처리했더니, 일부 데이터만 저장된 채 커밋돼 정합성이 깨졌어요. 어디서 예외를 던져야 롤백될지 점검해야 해요.
- 파일 업로드 후 DB 저장 로직에서 `IOException`이 발생했는데 DB에는 데이터가 남아 있어요. `rollbackFor` 누락 여부를 코드 리뷰에서 확인하는 상황이에요.
- 같은 서비스 안에서 `REQUIRES_NEW`로 감사 로그를 남기려 했는데 메인 롤백 때 같이 사라졌어요. self-invocation 때문이라 별도 빈으로 분리해야 해요.
