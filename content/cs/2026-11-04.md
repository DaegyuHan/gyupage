## 문제: 읽고 → 계산하고 → 쓰기

재고 1개 남은 상품에 요청 두 개가 동시에 들어오면 둘 다 `qty = 1`을 읽고, 둘 다 `0`으로 저장해요. 두 건이 팔렸는데 재고는 한 번만 줄었죠. 이게 **Lost Update**예요. `@Transactional`은 원자성을 보장할 뿐, 다른 트랜잭션과의 경쟁까지 막아 주지는 않아요.

```java
// 위험: 애플리케이션에서 계산한 값으로 덮어쓰기
@Transactional
public void decrease(Long id) {
    Stock s = repo.findById(id).orElseThrow();
    s.setQty(s.getQty() - 1);   // 둘이 같은 값을 읽음
}

// 안전: DB에서 조건부로 한 번에 처리
@Modifying
@Query("update Stock s set s.qty = s.qty - 1 where s.id = :id and s.qty > 0")
int decrease(@Param("id") Long id);   // 0이면 품절
```

## 해결책 3가지

| 방식 | 핵심 | 잘 맞는 상황 |
|---|---|---|
| 원자적 UPDATE | `qty = qty - 1` + 조건, 영향 행 수 확인 | 단순 증감, 가장 가볍고 먼저 고려 |
| 비관적 락 | `SELECT ... FOR UPDATE` (`PESSIMISTIC_WRITE`) | 충돌이 잦고 로직이 복잡할 때 |
| 낙관적 락 | `@Version`, 충돌 시 예외 후 재시도 | 충돌이 드문 경우(예: 프로필 수정) |

## 자주 하는 오해와 함정

- **"격리 수준만 올리면 되죠?"** MySQL InnoDB 기본값인 REPEATABLE READ에서도 일반 SELECT는 스냅샷 읽기라서, 읽은 값으로 계산해 덮어쓰면 Lost Update가 나요. PostgreSQL은 RR에서 충돌 시 serialization failure를 내지만, 어차피 재시도 코드가 필요해요.
- **`synchronized`로 막기**: 서버가 2대 이상이면 소용없어요. 락은 공유 지점인 DB(또는 분산 락)에 있어야 해요.
- **FOR UPDATE 조건에 인덱스가 없으면** 넓은 범위가 잠기거나 갭 락이 걸려 대기와 데드락이 늘어요.
- **낙관적 락 재시도**는 트랜잭션 바깥에서 해야 해요. 같은 트랜잭션 안에서 다시 시도하면 이미 오래된 스냅샷이에요.
- 여러 행을 잠글 땐 **항상 같은 순서**로 잠가야 데드락을 줄일 수 있어요.

<!-- practice -->
- 선착순 쿠폰 1,000장 이벤트에서 1,050장이 발급됐어요. 코드를 보니 `findById` 후 `count++` 방식이었고, 조건부 UPDATE나 비관적 락으로 고치고 동시성 테스트(`ExecutorService` + `CountDownLatch`)로 검증하는 상황이에요.
- 포인트 차감 API에서 `OptimisticLockingFailureException`이 간헐적으로 터져요. 재시도 횟수와 백오프를 어디서(서비스 바깥 파사드) 처리할지, 재시도해도 안전한(멱등한) 로직인지 코드 리뷰에서 짚어야 해요.
- 주문 처리 배치와 사용자 요청이 같은 재고 행을 서로 다른 순서로 잠가 데드락이 발생했어요. `SHOW ENGINE INNODB STATUS`로 원인을 확인하고, 락 획득 순서(ID 오름차순)를 통일하는 식으로 해결해요.
