## HashMap은 두 단계로 키를 찾아요
`get(key)`은 ① `hashCode()`로 버킷 위치를 정하고 ② 그 버킷 안에서 `equals()`로 같은 키를 찾아요. 그래서 **같다고 판단되는 두 객체는 반드시 같은 hashCode를 가져야** 해요(equals/hashCode 규약). 반대로 hashCode가 같다고 equals가 같을 필요는 없어요(충돌).

## 실무에서 터지는 세 가지 패턴
| 상황 | 증상 |
|---|---|
| equals만 재정의, hashCode 미재정의 | 같은 값인데 `get`이 null, Set에 중복 저장 |
| hashCode를 상수로 반환 | 한 버킷에 몰려 조회 O(n) (Java 8+는 트리화되지만 Comparable이 아니면 효과 제한적) |
| 키 필드가 나중에 바뀜 | 엔트리가 "유령"이 되어 조회도 삭제도 안 되고 메모리만 차지 |

세 번째가 가장 찾기 어려워요.

```java
Map<UserKey, String> map = new HashMap<>();
UserKey key = new UserKey("a");   // hashCode는 id 기반
map.put(key, "v");

key.setId("b");                   // 키 변경!
map.get(key);                     // null: 새 hash로 엉뚱한 버킷을 봄
map.get(new UserKey("a"));        // null: 버킷은 맞지만 equals가 false
```
저장 당시 hash 값으로 버킷에 들어가 있는데, 키가 바뀌어 어느 쪽으로 찾아도 못 찾아요.

## 자주 하는 오해와 해법
- **"Lombok @Data 붙이면 안전하다"**: 모든 필드로 hashCode를 만들기 때문에 가변 필드가 있으면 위 문제가 그대로 생겨요. 연관관계가 있는 JPA 엔티티는 순환 참조로 StackOverflow까지 나요.
- **JPA 엔티티**: 자동 생성 id는 persist 전엔 null이라 hashCode가 바뀌어요. 비즈니스 키(불변)를 쓰거나, id 기반이면 `hashCode`는 고정값, `equals`는 id가 null이 아닐 때만 비교하는 방식을 써요.
- **가장 좋은 해법은 키를 불변으로**: `String`, `Long`, `record`, enum을 키로 쓰면 이 문제가 구조적으로 사라져요.

<!-- practice -->
- 코드 리뷰에서 `@Data`가 붙은 DTO를 `Map` 키로 쓰는 PR을 봤어요. 필드가 중간에 setter로 바뀌는지 확인하고, `record`나 불변 키 객체로 바꾸자고 제안할 수 있어요.
- 캐시(`HashMap`/`ConcurrentHashMap`)의 크기가 계속 늘고 hit rate는 낮은 장애가 났어요. 키 객체의 hashCode/equals 불일치나 키 변경으로 중복·유령 엔트리가 생겼는지 힙 덤프로 확인해요.
- 연관관계가 있는 JPA 엔티티를 `Set`에 담았더니 persist 이후 `contains`가 false로 나오거나 중복이 들어가요. id 기반 hashCode가 persist 전후로 달라지는 게 원인인지 확인해요.
