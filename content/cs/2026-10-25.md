## 에러의 정체: 막는 쪽은 서버가 아니라 브라우저예요
브라우저에는 **동일 출처 정책(Same-Origin Policy)**이 있어요. 출처(scheme + host + port)가 다른 곳의 응답을 JS가 마음대로 읽지 못하게 막는 규칙이에요. CORS는 이걸 서버가 헤더로 "이 출처는 읽어도 돼요"라고 풀어주는 약속이에요.

그래서 curl이나 Postman, 서버 간 호출에서는 CORS 에러가 안 나요. 심지어 단순 요청(simple request)은 **서버까지 요청이 도착하고 처리도 끝난 뒤**, 브라우저가 응답을 JS에 안 넘겨줄 뿐이에요. "에러가 났는데 DB에는 데이터가 들어가 있네?" 하는 상황이 여기서 나와요.

## Preflight는 언제 날아갈까요?
조금 위험해 보이는 요청은 브라우저가 본 요청 전에 `OPTIONS`로 먼저 물어봐요.

| 요청 특징 | Preflight |
|---|---|
| GET/POST/HEAD + 기본 헤더 + form 계열 Content-Type | 없음 |
| PUT/PATCH/DELETE | 발생 |
| `Content-Type: application/json` | 발생 |
| `Authorization` 등 커스텀 헤더 | 발생 |

```
OPTIONS /orders
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type
```

서버가 허용 헤더로 응답하면 그제서야 본 요청이 나가요. JSON API를 쓰면 거의 항상 preflight가 붙는다고 보면 돼요.

## 실무에서 자주 터지는 지점
- **OPTIONS가 인증 필터에 걸려요.** preflight에는 토큰이 없어서 401이 나고, 브라우저는 이를 CORS 실패로 보여줘요. CORS 처리를 인증보다 앞에 두세요.
- **쿠키를 쓰면 `*`가 금지예요.** `credentials: 'include'`일 때는 `Allow-Origin`에 구체적인 출처를, `Allow-Credentials: true`를 함께 줘야 해요.
- **헤더 중복이에요.** Nginx와 앱 양쪽에서 헤더를 붙이면 값이 두 번 들어가 브라우저가 거부해요.
- **매번 OPTIONS가 날아가요.** `Access-Control-Max-Age`로 preflight 결과를 캐싱하면 지연이 줄어요.

마지막으로, CORS는 서버를 지키는 보안 장치가 아니에요. 다른 출처의 JS가 응답을 읽는 걸 막을 뿐이라, 악의적인 클라이언트나 CSRF는 별도로 막아야 해요.

<!-- practice -->
- 프론트에서 "CORS 에러"라고 하는데 서버 로그에는 요청이 정상 처리되어 있어요. 단순 요청이라 서버는 처리했고 브라우저가 응답만 막은 건 아닌지, 응답의 Allow-Origin 헤더부터 확인해요.
- 로그인 쿠키를 붙여 API를 호출하자 갑자기 CORS가 깨져요. Allow-Origin이 `*`로 되어 있는지, Allow-Credentials가 빠졌는지, 프론트의 credentials 옵션과 맞는지 점검해요.
- Spring Security 도입 후 모든 API가 preflight에서 401이 나요. OPTIONS 요청이 인증 필터에 걸린 것이므로 CORS 설정을 필터 체인 앞단에 적용해요.
