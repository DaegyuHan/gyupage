## 개념: 이론상 복잡도는 이렇게 달라요

| 연산 | ArrayList | LinkedList |
|---|---|---|
| get(i) | O(1) | O(n) |
| 맨 뒤 add | amortized O(1) | O(1) |
| 맨 앞 add/remove | O(n) (shift) | O(1) |
| 중간 삽입/삭제 | O(n) | **찾는 데 O(n)** + 연결 O(1) |
| contains | O(n) | O(n) |

핵심은 LinkedList의 "삽입이 O(1)"이 **이미 그 노드를 잡고 있을 때**만 성립한다는 점이에요. 인덱스로 중간에 넣으려면 먼저 노드까지 걸어가야 해서 결국 O(n)이에요.

## 왜 중요한가: 실무에서는 상수 비용이 승부를 가려요

- ArrayList는 연속된 메모리라 CPU 캐시 적중률이 높고, `System.arraycopy`로 shift를 통째로 처리해요.
- LinkedList는 요소마다 Node 객체(헤더 + prev/next 참조)가 생겨서 메모리를 더 쓰고, GC 부담도 커지고, 포인터를 따라가다 캐시 미스가 나요.
- 그래서 같은 O(n)이어도 ArrayList가 몇 배 빠른 경우가 흔해요. 그래서 "일단 ArrayList, 큐/덱이 필요하면 ArrayDeque"가 기본 선택이에요.

```java
// 큐 용도: ArrayList.remove(0)은 매번 전체 shift → O(n)
Queue<Task> q = new ArrayDeque<>();   // 양 끝 O(1), 노드 할당 없음

// 반복 contains: 리스트면 O(n*m)
Set<Long> blocked = new HashSet<>(blockedIds);
List<Order> ok = orders.stream()
    .filter(o -> !blocked.contains(o.userId()))
    .toList();
```

## 자주 하는 오해/함정

- **"중간 삽입이 잦으니 LinkedList"**: 삽입 위치를 찾는 비용이 지배적이라 대부분 이득이 없어요. `ListIterator`로 순회하며 바로 끼워 넣는 경우만 예외예요.
- **LinkedList에 `for (int i...) list.get(i)`**: 매번 처음부터 걸어서 O(n²)이 돼요. 향상된 for나 Iterator를 써야 해요.
- **LinkedList는 큐니까 좋다?** 단순 큐/스택이면 ArrayDeque가 보통 더 빠르고 가벼워요. (단, null 요소는 불가)
- **ArrayList의 add도 가끔 느려요**: 용량이 차면 1.5배로 재할당해서 복사해요. 크기를 아는 대량 적재라면 `new ArrayList<>(size)`로 미리 잡아 두세요.

<!-- practice -->
- 배치에서 100만 건 리스트를 `while (!list.isEmpty()) process(list.remove(0))`으로 처리했더니 데이터가 늘수록 급격히 느려졌어요. 매번 전체 shift가 일어난 거라 ArrayDeque나 인덱스 순회로 바꿔야 해요.
- 코드 리뷰에서 "중간 삽입이 많으니 LinkedList로 했어요"라는 설명을 봤어요. 삽입 위치를 인덱스로 찾고 있다면 이점이 없으니, 실제 벤치마크(JMH)나 대안 구조를 근거로 같이 이야기해 볼 수 있어요.
- 주문 목록(만 건)에서 차단 사용자 목록(List)을 `contains`로 매번 비교해 API가 느려졌어요. 차단 목록을 HashSet으로 바꾸면 O(n*m)이 O(n)이 돼요.
