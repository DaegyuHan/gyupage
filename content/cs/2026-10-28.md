## 복합 인덱스는 '전화번호부'예요
`(user_id, created_at)` 인덱스는 user_id로 먼저 정렬하고, user_id가 같은 데이터끼리 created_at으로 정렬해요. 성을 먼저 찾고 그 안에서 이름을 찾는 전화번호부와 같아요. 그래서 **선두 컬럼부터 순서대로** 써야 B-Tree를 잘 타요. 이걸 Leftmost Prefix 규칙이라고 불러요.

| 쿼리 조건 | 인덱스 활용 |
|---|---|
| `user_id = ?` | 좋음 |
| `user_id = ? AND created_at >= ?` | 두 컬럼 모두 범위 탐색에 사용 |
| `user_id = ? ORDER BY created_at DESC` | 정렬까지 인덱스로 해결(filesort 없음) |
| `created_at >= ?` 만 | 선두 컬럼이 없어 비효율적 (MySQL 8.0의 skip scan은 예외적인 경우) |

```java
@Table(indexes = @Index(name = "idx_orders_user_created",
        columnList = "user_id, created_at"))
public class Order { /* ... */ }

public interface OrderRepository extends JpaRepository<Order, Long> {
    // WHERE user_id = ? ORDER BY created_at DESC LIMIT 20
    List<Order> findTop20ByUserIdOrderByCreatedAtDesc(Long userId);
}
```

## 실무에서 왜 중요한가요?
내 주문 목록, 내 알림 목록처럼 "특정 사용자의 최근 N건" 패턴은 거의 모든 서비스에 있어요. 단일 인덱스 두 개를 따로 만드는 것보다 복합 인덱스 하나가 훨씬 빠르고, 정렬 비용도 없애 줘요. 반대로 순서를 잘못 잡으면 인덱스가 있는데도 느려서 장애로 이어져요.

## 자주 하는 오해와 함정
- **"카디널리티 높은 컬럼을 무조건 앞에"**: 절반만 맞아요. 먼저 **등치(=) 조건 컬럼을 앞에**, **범위 조건 컬럼은 뒤에** 두고, 그다음에 카디널리티를 봐요.
- **범위 조건 뒤의 컬럼**: `a = ? AND b > ? AND c = ?`에서 (a, b, c) 인덱스를 쓰면 c는 범위를 좁히는 데 쓰이지 못하고 필터링에 그쳐요.
- **컬럼 가공**: `DATE(created_at) = ?`처럼 컬럼에 함수를 씌우면 인덱스를 못 타요. 범위 조건(`>= ? AND < ?`)으로 바꿔야 해요.
- **인덱스는 공짜가 아니에요**: 쓰기 시 갱신 비용과 디스크를 써요. 쿼리 패턴을 기준으로 필요한 것만 만들어요.
- **확인은 `EXPLAIN`으로**: `key`, `key_len`(몇 개 컬럼까지 썼는지), `Extra`(Using filesort, Using index)를 꼭 봐요.

<!-- practice -->
- 슬로우 쿼리 알람이 울려서 보니 `WHERE created_at BETWEEN ...` 조회가 느려요. 인덱스는 `(user_id, created_at)`뿐이에요. 이 쿼리에 맞는 `created_at` 단독 인덱스가 필요한지, 아니면 쿼리를 바꿀지 EXPLAIN으로 판단해요.
- 코드 리뷰에서 `WHERE DATE(created_at) = '2024-01-01'`을 발견했어요. 인덱스를 못 타는 이유를 설명하고 `created_at >= ? AND created_at < ?` 형태로 바꾸자고 제안해요.
- 목록 API에 `ORDER BY created_at DESC LIMIT 20`이 있는데 EXPLAIN에 `Using filesort`가 떠요. `(status, created_at)`처럼 조건과 정렬 컬럼을 묶은 복합 인덱스로 개선해요.
