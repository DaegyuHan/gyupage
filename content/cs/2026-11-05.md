## 증상: 에러 로그는 없는데 502만 간헐적으로 떠요

트래픽이 많지 않은 새벽이나 배포 직후에 ALB·Nginx가 가끔 502를 반환하는데, 애플리케이션 로그에는 요청 자체가 안 남아 있는 경우가 있어요. 원인 후보 1순위가 **Keep-Alive 커넥션 경쟁 상태(race)** 예요.

## 개념: 누가 먼저 끊는가

HTTP Keep-Alive는 TCP 커넥션을 재사용해서 매 요청마다 3-way handshake를 하지 않게 해 줘요. 문제는 **유휴(idle) 커넥션을 양쪽이 각자의 타이머로 닫는다**는 점이에요.

1. LB가 백엔드와 맺은 커넥션을 재사용하려고 요청을 보내요.
2. 바로 그 순간 서버(Tomcat)의 keep-alive 타임아웃이 만료되어 FIN을 보내요.
3. 이미 닫힌 소켓에 요청이 도착하면 서버는 RST로 응답하고, LB는 502를 내보내요.

| 구간 | 대표 설정 | 기본값 예시 |
|---|---|---|
| LB | idle timeout | ALB 60초 |
| Tomcat | `server.tomcat.keep-alive-timeout` | 미설정 시 connection-timeout(보통 60초)을 따라감 |

두 값이 같거나 서버가 더 짧으면 경쟁이 생겨요. **원칙은 "연결을 먼저 끊는 쪽이 클라이언트 쪽(LB)이어야 한다"**, 즉 서버 keep-alive > LB idle timeout 이에요.

## 실무 함정: 서버 호출 클라이언트도 같은 문제예요

내 서비스가 다른 서버를 부를 때도 똑같아요. 커넥션 풀에 남아 있던 죽은 커넥션을 꺼내 쓰면 `NoHttpResponseException`, `Connection reset`이 나요.

```java
var cm = PoolingHttpClientConnectionManagerBuilder.create()
    .setDefaultConnectionConfig(ConnectionConfig.custom()
        .setTimeToLive(TimeValue.ofSeconds(30)) // 상대 서버 keep-alive보다 짧게
        .build())
    .build();
CloseableHttpClient client = HttpClients.custom()
    .setConnectionManager(cm)
    .evictIdleConnections(TimeValue.ofSeconds(20))
    .build();
```

- **자주 하는 오해**: "타임아웃 에러가 아니니 서버 성능 문제겠지" → 실제로는 서버가 멀쩡해도 발생해요.
- **재시도로 덮기**: POST 같은 비멱등 요청을 무작정 재시도하면 중복 처리 위험이 있어요. 먼저 타임아웃 정합성을 맞추세요.
- 클라이언트 풀의 TTL은 상대 서버 keep-alive보다 **짧게** 잡아요.

<!-- practice -->
- 배포 직후나 새벽 저트래픽 시간대에만 ALB 502가 간헐적으로 올라와요. 앱 로그엔 흔적이 없다면 ALB idle timeout(60초)과 Tomcat keep-alive timeout을 비교하고, Tomcat을 더 길게(예: 75초) 맞춰 보세요.
- RestTemplate/HttpClient로 외부 API를 호출하는데 하루에 몇 번씩 `NoHttpResponseException`이 나요. 풀의 유휴 커넥션이 상대 서버에서 이미 닫힌 경우라서, TTL·evictIdleConnections 설정을 점검해야 해요.
- 코드 리뷰에서 "502 나니까 재시도 3회 넣었어요"라는 PR을 받았어요. 결제·주문 같은 비멱등 POST라면 중복 실행 위험이 있으니, 재시도 전에 원인(타임아웃 불일치)부터 해결하고 멱등키를 도입하자고 제안할 수 있어요.
