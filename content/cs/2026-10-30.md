## JWT가 stateless라는 말의 진짜 의미
JWT는 서명된 토큰이라 서버가 세션 저장소를 조회하지 않고 서명과 만료 시간만 검증하면 돼요. 서버를 여러 대로 늘려도 세션 공유가 필요 없죠. 하지만 뒤집어 말하면 **한 번 발급한 토큰은 만료 전까지 서버가 "취소"할 방법이 기본적으로 없다**는 뜻이에요.

## 실무에서 왜 문제가 될까요?
- 로그아웃해도 토큰을 가진 사람은 만료 때까지 API를 호출할 수 있어요.
- 토큰이 탈취되면 비밀번호를 바꿔도 막을 수 없어요.
- 권한이 바뀌어도 payload의 옛 role이 그대로 쓰여요.

그래서 보통 이렇게 설계해요.

| 구분 | Access Token | Refresh Token |
|---|---|---|
| 수명 | 5~30분 | 1~2주 |
| 저장 | 메모리 | HttpOnly+Secure 쿠키 |
| 서버 상태 | 없음 | Redis/DB에 저장 |

Access는 짧게 살게 해서 피해를 제한해요. 상태는 Refresh에만 두고, 로그아웃 시 이걸 삭제해요. 재발급 때마다 Refresh를 새로 발급하고 이전 것을 폐기하는 **Rotation**을 쓰면, 폐기된 토큰이 다시 들어올 때 탈취로 보고 해당 사용자의 토큰을 전부 무효화할 수 있어요.

```java
public TokenPair reissue(String refreshToken) {
    String userId = jwtProvider.getSubject(refreshToken);
    String saved = redis.opsForValue().get("RT:" + userId);
    if (!refreshToken.equals(saved)) {
        redis.delete("RT:" + userId); // 재사용 감지 → 전체 폐기
        throw new InvalidTokenException();
    }
    return issueAndStore(userId); // 새 Access + 새 Refresh
}
```

## 자주 하는 오해와 함정
- "JWT는 암호화돼 있어요" → 아니에요. 기본은 서명일 뿐, payload는 Base64 디코딩으로 누구나 읽어요. 비밀번호 같은 민감 정보를 넣으면 안 돼요.
- "localStorage에 넣으면 편해요" → XSS 한 번이면 털려요. 쿠키는 반대로 CSRF를 고려해야 해요(SameSite 설정).
- "블랙리스트를 쓰면 stateless가 깨져요" → 맞아요. 하지만 즉시 차단이 꼭 필요하면 남은 수명만큼만 jti를 저장하는 절충이 현실적이에요.
- alg 검증을 빼먹거나 서명 키를 코드에 하드코딩하는 것도 단골 실수예요.

결국 JWT냐 세션이냐보다 **즉시 폐기가 얼마나 필요한가**를 기준으로 고르는 게 핵심이에요.

<!-- practice -->
- 사용자가 "로그아웃했는데 다른 기기에서 계속 접속돼요"라고 문의해요. Refresh Token을 기기별로 저장하고 있는지, 로그아웃 시 Redis 키를 삭제하는지 확인하고, Access 만료 시간이 너무 길지 않은지 점검해요.
- 코드 리뷰에서 로그인 응답의 JWT payload에 이메일, 전화번호, 권한 목록이 통째로 들어간 걸 발견해요. 누구나 디코딩해 볼 수 있으니 userId와 최소한의 클레임만 담도록 수정을 요청해요.
- 장애 대응 중 Refresh 재발급 API에 요청이 몰려 Redis 부하가 커졌어요. Access 만료가 1분으로 너무 짧게 설정된 게 원인이라, 적절한 수명으로 조정하고 클라이언트가 만료 직전에 한 번만 재발급하도록 단일 요청 처리를 넣어요.
